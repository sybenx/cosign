# Keykin Core test vectors

For [Keykin Core](../core.md) draft 13.1, §14. Two kinds of vector live here:

- **Computed vectors** in [`vectors.json`](vectors.json), generated by
  [`gen_vectors.py`](gen_vectors.py). That script is pure Python with no dependencies; run it with
  `python3 -I gen_vectors.py > vectors.json`. Every input is fixed, so anyone can regenerate the file
  and diff it. These cover the parts of Core that are plain hashing and curve arithmetic.
- **Behaviour cases** listed below. A second implementation must pass each one, but their expected
  outputs come from running a reference implementation, which does not exist yet. When it does, its
  output for each case goes into `vectors.json` beside the computed ones.

Done (Phase 1) when the TypeScript and Kotlin implementations both pass every vector, and a fuzzed
parser has run against every message type in core §9.4 and `refresh.md` §7.

## Computed vectors (`vectors.json`)

| Key | Core § | What it pins |
|---|---|---|
| `join_check` | 4.1 | The 6-digit join check from `g, m, n, s, t`. A second case changes only `t`, which changes the code. |
| `list_hash` | 6.1, 6.7.2 | JCS and SHA-256 of a list: a single `add`, and a seat change with its redeal placeholder. |
| `pair_code` | 6.2 | The typed two-device code from `g`, the list hash and `r`. |
| `indices` | 3.2 | The three hash-derived indices of an added device, plus their 32-byte identifier encoding. |
| `wait_ids` | 6.3 | The hold and recovery wait ids. |
| `lock_challenge` | 6.1 | The WebAuthn `clientData.challenge` for a destructive sign, an account change (list hash, epoch id, expiry) and a cancel. |
| `waited_statement_digest` | 6.3 | The digest a server signs for a waited statement. |
| `commitment_rebuild` | 3.4 step 4 | A device rebuilding `C0…C3` from its own 3 points and `C0`. Includes a negative case (a tampered `C2` must be refused) and derived `P_i` for indices 4, 5, 6 and a hashed index. |
| `ecdh_dleq` | 5.5, 6.7.1 | One weighted decryption answer with its proof. Negatives: a changed `z`, a repeated index, `Q` the identity. |
| `future_dates` | 5.7 item 4 | Which kinds may be dated ahead. |
| `stateless_destructive` | 5.8 | What needs an approval or a hold. |
| `lifetimes` | 5.6 | Age limits per class (lifetime plus 30 s), a class not allowed for a type, and a request dated ahead. |
| `helper_seat` | 3.1 | The helper's three reserved seat indices. |
| `redeal_apply` | 6.7.1 | A redeal's `D`, the new `C_S`, a device's delta check, and the `δ(b)·G` values for a re-issued paper item. |
| `data_key` | 4.5 | `dk(S)` from the base key and sorted seeds. |
| `signpost` | 6.7.5 | Its `d`, `h` and device-copy key. |
| `seated_reply_digest` | 6.7.5 | What a server's `seated?` reply signature covers. |

Notes:

- The `ecdh_dleq` vector uses a fixed proof nonce `k` so it can be checked. A real implementation
  hedges `k` (core §5.5), and a vector for that is the "same random state, different request" case
  below.
- The "group key" in these files is a test point whose private key the generator knows. That never
  happens in a real account.

## Behaviour cases (outputs from the reference implementation)

Each case is a sequence of messages and the expected accept or refuse, with the error code.

1. **Signing round** (§5.1–5.3)
   - The one-call round for a device (3 indices) plus a server (1), with an even group key and with a
     signing nonce `R` of odd y.
   - The two-call round for the backup plus two servers, using `after`.
   - A bad partial is named by member.
   - `signers` is not exactly the participants.
   - The commitments miss an index or contain the identity.
   - A byte-identical retry gets the cached answer.
   - A retry with the same id but a different body gets `id_reused`.
   - A second `sign` for the same `after` is refused.
2. **Nonces** (§5.2)
   - The same OS randomness with two different requests gives two different nonces, on the co-signer
     side and on the coordinator side.
   - The same holds for the DLEQ `k`.
3. **Epoch records and changes** (§3)
   - An epoch record with the wrong kind or `d`, or tags that disagree with the content, is refused.
   - A kind 1 whose content looks like a record is not a record.
   - A record whose commitment a device cannot rebuild is refused.
   - Each of the invariants I1–I5 broken is refused.
   - A change from an approver who is a helper is refused.
   - A change naming the previous epoch:
     - a `remove` within 7 days of the commit is accepted;
     - an `add` is refused;
     - a `remove` after 7 days is refused.
   - Two changes claiming one index: both adds are void.
   - Two lock changes replacing the same lock: both void.
   - Catch-up takes the union, so a server leaving out a removal changes nothing.
4. **Joining** (§4)
   - The honest flow in both directions.
   - A racer's hello: the typed check does not match.
   - A join-code hello not sealed by `n` is refused.
   - A welcome from a stranger is refused.
   - An epoch record for another group is refused.
   - The inviter's sigma is missing.
   - A summed share that misses the commitment.
5. **Locks** (§6.1)
   - A valid assertion for each kind of `what`.
   - The UV flag is missing.
   - The `rp` is wrong.
   - The challenge is over a different body.
   - A destructive approval reused at a second co-signer is allowed.
6. **Approvals and waits** (§6.2, §6.3)
   - Each row of the approval table, met and not met.
   - A `pair` whose typed code does not match.
   - A `paper` approval whose challenge is stale at the co-signer.
   - A `recovery` approval submitted from a connection other than the holder's.
   - A waited statement shorter than `W`.
   - A hold cancelled by a locked device.
   - A recovery that ends running holds.
   - A missed `cancel`: the server catches up before issuing a statement.
   - A dead peer is skipped after an hour.
7. **Report lost** (§6.4)
   - Removal by `lock`, `pair` and `paper`.
   - A lockless single device trying to report is refused.
   - Rounds with a removed member are refused at once.
   - `deliver` from a removed member is refused.
8. **Recovery** (§6.5)
   - The full flow, ending in a refresh.
   - Backup material whose inner layer does not match the `backup` hash is refused.
   - Session limits: an ordinary event during a session is refused.
9. **Destructive rule and lifetimes**: the computed tables above, played through a server.
10. **Push and inbox** (§8)
    - Payload padding and the size limit.
    - The server's signature is checked.
    - A separate address per class.
    - Addresses are dropped on removal.
    - `deliver` with a `p` tag that is not `to` is refused.
    - Inbox caps never drop deliveries or wait notices.
11. **Transport** (§9)
    - Chunking and reassembly by sender.
    - A 513 KB message is refused.
    - An expired part is dropped.
    - Share-bearing messages are never sent as kind 1059.
12. **Upkeep** (core §6.7)
    - Seat replacement gives the same share value at the same index; every server ever seated is still
      3 points in one state.
    - A redeal: delta checks, `C_S` rebuilt from a device's own points, old share destroyed, `stale`
      and catch-up.
    - Mandatory redeal: a `[seat]` or `[remove]` list without one is refused; a `self` remove without
      one is accepted.
    - Seat conflicts: same `new` counts once; different `new` voids both.
    - Paper: an approval without `inner`, then the commit with `inner` and material; two paper changes,
      the lowest hash wins; a missing paper delta is caught after apply.
    - `rerepair` allowed and refused cases; `need_repair` gives the same value twice.
    - F3 with no co-sign accepted only by `pair` or `paper`.
    - Signpost: a site's request to sign or delete one (current or past `d`) is refused; servers
      ignore it entirely.
    - Dealer uploads without a valid approval are refused; inert uploads expire.
    - Release seeds: concurrent redeals' items union, and recovery opens each with its own seed;
      `dk(S)` derivation (add to `gen_vectors.py`).
    - `need_repair` answered by two devices, or a device and the paper; refused for a non-current
      holder.
    - A removal's stranded redeal is re-dealt, never stepped back past.
